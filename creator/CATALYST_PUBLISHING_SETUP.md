## Install order

Create or replace these Default namespace functions from `creator/functions`:

1. `handoff_publication_to_catalyst(jobId: int)`
2. `validate_catalyst_publication_request(...)`
3. `record_catalyst_publication_result(...)`
4. `publish_approved_article(articleId: int)`
5. `schedule_approved_article(articleId: int, scheduledAtText: string)`
6. `retract_published_article(articleId: int, reason: string, replacementPath: string)`
7. `process_scheduled_publication(articleId: int)`
8. `process_scheduled_publications()`

The first three are Catalyst-only boundaries. Publish, schedule, retract, and
the two reconciliation helpers replace Creator-local publication code.
No Creator function may directly mark an article or revision Published except
the signed callback function.

Before installing retraction, add `Unpublished` to `Articles.Workflow_State` and
add `Retraction_Reason` (multi-line) plus `Replacement_Path` (single line, 255)
to `Publication_Jobs` and its report.

## Application variables

Create a `Publishing` variable group with environment-specific values:

- `Catalyst_Base_URL`: the AppSail base URL, with no trailing slash.
- `Signing_Secret`: a random value of at least 32 characters, matching
  `PUBLISHING_HMAC_SECRET` in Catalyst.

The supplied functions reference them as
`thisapp.variables.Publishing.Catalyst_Base_URL` and
`thisapp.variables.Publishing.Signing_Secret`. Confirm Creator inserts the exact
variable reference generated by its Deluge editor; do not replace either value
with a string literal in source control. Restrict variable administration to the
owner/deployment operator.

Do not paste the OAuth client secret or refresh token into Creator. Those belong
only in Catalyst AppSail environment variables. Creator stores only the AppSail
base URL and the shared publication-signing secret.

## Private Custom APIs

Keep the existing user-facing APIs private OAuth2:

- `publish_approved_article`
- `schedule_approved_article`
- `retract_published_article`

Create two Catalyst-only Custom APIs. Both must be POST, `application/json`, Key
and Value arguments, OAuth2, Standard response, and unavailable through Public
Key authentication.

`retract_published_article` is also POST, `application/json`, Key and Value
arguments, OAuth2, Standard response, and unavailable through Public Key. Only
an active Publisher or Editorial Admin may invoke it. A reason is required; the
optional replacement must be an application-local path beginning with `/`.

### Validate Catalyst Publication Request

Link name: `validate_catalyst_publication_request`

Arguments, all strings:

- `creatorJobId`
- `idempotencyKey`
- `articleRecordId`
- `articleUuid`
- `revisionRecordId`
- `revisionUuid`
- `documentChecksum`

This is the execution-time authorization boundary. Catalyst calls it immediately
before an immutable write. It rejects closed jobs, state changes, approval
revocation, pointer changes, UUID mismatches, and checksum changes.

### Record Catalyst Publication Result

Link name: `record_catalyst_publication_result`

Arguments:

- strings: `eventId`, `requestId`, `creatorJobId`, `idempotencyKey`, `status`,
  `publicationId`, `objectId`, `publishedAt`, `nextRetryAt`, `errorCode`,
  `errorMessage`, `mediaJson`, `callbackTimestamp`, `callbackNonce`,
  `callbackSignature`
- integer: `attemptCount`

The OAuth connection authenticates Catalyst to Creator. The callback HMAC binds
the complete result body and protects against body substitution. `eventId` is
stored as the unique `Audit_Events.Event_UUID`, so replay converges.

## Media snapshot and Stratus rule

The handoff reads the exact approved `Editor_Document` bytes and includes each
referenced non-failed/non-archived media record, plus featured and social media.
The Article Workspace writes the canonical document's distinct media UUIDs into
`Article_Revisions.Referenced_Media_UUIDs` on every save. The handoff uses that
bounded list for an exact Creator query instead of scanning the complete media
library. It adds featured/social UUIDs, removes duplicates, and rejects more than
200 assets in one revision.
Every included asset must still have its Creator `Draft_File`, stable
`Media_UUID`, original filename, one supported MIME type (`image/jpeg`,
`image/png`, `image/gif`, or `image/webp`), file size, width, height, SHA-256
checksum, and alt text. A pre-existing `Published_URL` is not required.

At execution, Catalyst downloads the exact file from `Media_Assets_Report` using
the narrow `ZohoCreator.report.READ` OAuth scope. It validates file signature,
size, checksum, and dimensions, then writes the bytes to the public Stratus
bucket using a content-addressed immutable key. The signed success callback
contains `mediaJson`; Creator verifies each record ID, media UUID, and checksum
before setting `Published_Object_Key`, `Published_URL`, and `Status = Ready`.
Catalyst rejects a missing inline source mapping before accepting the handoff.
The revision payload also preserves `featuredMediaId` and `socialMediaId`, so the
later public frontend can resolve the correct immutable cover/social object
without consulting Creator.
Before installing the handoff, add the multi-line
`Article_Revisions.Referenced_Media_UUIDs` field and expose it in
`Article_Revisions_Report`. Upload the rebuilt
`editor-widget/zet/dist/zet.zip`, then re-save any existing image-bearing draft
before it enters review. An older approved document with inline media but no
normalized reference list must not be published; return it to a draft through
the normal workflow and save it again.

Confirm `Media_Assets_Report` exposes `Draft_File`, media UUID, filename, MIME,
size, width, height, checksum, alt/caption/credit, published object key/URL, and
status to the OAuth integration identity. Normal editorial profiles should not
gain broader report access merely to support this server connection.

## Scheduling switch

Catalyst owns the due time. Disable the old Creator date-field workflow that
mutated records at `Articles.Scheduled_At`. Do not call a local publication body.

Create one low-frequency daily Creator custom schedule for
`process_scheduled_publications`. The current Creator 6 custom-schedule UI
supports Daily, Weekly, Monthly, Yearly, or Once, so Daily is the shortest
supported interval here. It retries only Creator-to-Catalyst handoffs that were
never acknowledged. It does not execute due publication and never marks content
Published. Immediate handoff still occurs when publish or schedule is requested;
this daily workflow is only a last-resort reconciliation sweep.

`process_scheduled_publication(articleId)` is retained only as a safe manual
redelivery/status helper for an open schedule job.

## Creator callback effects

- `Retrying`: job remains Processing with attempt/error metadata.
- `Succeeded`: completes the Catalyst job. If the exact approval is still
  current, it supersedes the old published revision, moves the exact revision
  and article to Published, updates pointers/timestamps, and appends the normal
  publication audit event. If Creator changed in the post-preflight race window,
  it preserves that newer Creator state and writes `Catalyst Publication State
  Conflict` for operator reconciliation instead of retrying an already-committed
  publication forever.
- `Failed`: completes the job with error data; a Scheduled article returns to
  Approved if the same approved pointer is still current.
- Successful `Unpublish`: keeps the revision and immutable publication identity,
  moves the Article from Published to Unpublished, and writes `Catalyst Article
  Retracted`. The Catalyst pointer records the reason and optional replacement.

Notification sends happen after state/audit work and are best effort.
